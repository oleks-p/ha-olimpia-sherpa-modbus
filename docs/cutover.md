# Cutover: from YAML-driven Sherpa entities to the integration

How a live Home Assistant moves from the generated / hand-written YAML setup
(a `modbus:` hub plus template, derivative and threshold sensors) to
`olimpia_sherpa_modbus`, **keeping every entity id, its history and its
long-term statistics**.

Rehearsed end to end on 2026-10-13, on a replica of the reference site: HA
2026.8.2 with the site's own `plant.yaml` and `sherpa.yaml`, pointed at the
simulator. Results:
- `cutover.py verify` passed: 50 legacy entities, 19 statistics series.
- In the database, `sensor.sherpa_water_in` kept its `states_meta` row and its
  `statistics_meta` row (same ids, unit unchanged).
- The next 5-minute compile appended to the same series, with no duplicate
  series.
- The entity was unavailable for 22 s.

## Why it works, and the one thing that must not go wrong

History is keyed by entity id. The integration suggests the legacy ids
explicitly, and Home Assistant uses a suggested id as it stands. An id is taken,
though, while **any** registry entry holds it, and HA keeps the YAML setup's
registry entries long after the YAML is gone. If the integration were added
first, every entity would land on `…_2`, and its history would split from the
old entity's. So the order is fixed:

1. Retire the YAML and restart, so the old entities have no source.
2. Remove the old registry entries (`cutover.py remove-legacy`).
3. Add the integration (`cutover.py add`).

## The window (reference site)

HA is down for the backup and the file changes, about 1-2 minutes. The Sherpa
reads are missing for about 3 minutes, until the entry is added. The heat pump
runs on its own controller throughout.

```bash
C="sudo -n docker compose -f /home/user/homeassistant/docker-compose.yml"
CFG=/home/user/homeassistant/config
B=/home/user/homeassistant/backups/cutover-$(date +%Y%m%d-%H%M%S)

# 1. stop, and confirm it stopped (exit codes lie here; check the state)
$C stop homeassistant && test -z "$($C ps -q --status running homeassistant)"

# 2. back up what the cutover touches, with HA stopped so the DB is consistent.
#    sudo: .storage/ files are root-owned (the container runs as root), and a
#    restore must put them back exactly as they were.
mkdir -p $B && sudo -n cp -a $CFG/.storage $CFG/packages $CFG/dashboards \
  $CFG/configuration.yaml $CFG/custom_components $CFG/home-assistant_v2.db* $B/

# 3. install the pinned release; 4. retire the YAML, deploy the new files
tar -xzf ~/cutover/olimpia_sherpa_modbus-0.1.0.tar.gz -C $CFG/
mv $CFG/packages/sherpa.yaml $B/sherpa.yaml.retired
cp ~/cutover/plant.yaml $CFG/packages/plant.yaml
cp ~/cutover/boiler.yaml $CFG/dashboards/boiler.yaml

# 5. start, and confirm it is running
$C start homeassistant && sleep 5 && test -n "$($C ps -q --status running homeassistant)"
```

Then from the workstation, once the API answers:

```bash
T="--ha http://192.168.30.141:8123 --token-file ~/.config/hvac-platform/ha-token --plan cutover-plan.json"
uv run --no-project --with websockets -- python tools/cutover.py $T remove-legacy --yes
uv run --no-project --with websockets -- python tools/cutover.py $T add --serial-port /dev/ttyUSB0
sleep 60
uv run --no-project --with websockets -- python tools/cutover.py $T verify      # must print OK
```

After that:
- Push the regenerated plant dashboard from the platform:
  `tools/push_dashboard.py --site sites/ua-kyiv-house-01 --board plant --lang uk`.
- Confirm the platform's registry sync has nothing to do for the Sherpa:
  `python -m core --site sites/ua-kyiv-house-01 --sync-registry --dry-run`.
- Check the unit: both alarm words read 0 (no E09), and the values match the
  display.

## Rollback

- **Before `remove-legacy`:**
  1. Stop HA.
  2. Copy back `packages/plant.yaml` and `dashboards/boiler.yaml` from the
     backup, and restore `packages/sherpa.yaml` from `sherpa.yaml.retired`.
  3. Delete `custom_components/olimpia_sherpa_modbus`.
  4. Start HA.
- **After it:**
  1. Stop HA.
  2. Restore `.storage/` (registry, config entries and restore state),
     `packages/` and `dashboards/` from the backup, with `sudo cp -a` so
     ownership comes back as it was.
  3. Delete `custom_components/olimpia_sherpa_modbus`.
  4. Start HA.

  The database can stay: any rows written since the backup are harmless. Restore
  `home-assistant_v2.db*` as well for an exact return to the backup point.

## Afterwards

- **Retired YAML:** `sherpa.yaml` stays in the backup directory, not in
  `packages/`. Anything copied back into `packages/` would bring the second
  Modbus client back.
- **`smarthome lights/tools/deploy.sh`** still generates `boiler.yaml` and other
  boards with **pre-sync ids** (`sherpa_circulation_pump`, …). Running it would
  overwrite the boards on the host with bindings that do not exist, cutover or
  not. Update its generator or stop using it for these boards.
